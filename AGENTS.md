# AGENTS.md

This file provides guidance to AI coding agents (including Claude Code, via `CLAUDE.md`'s import of this file) when working with code in this repository.

## What this is

A Chrome/Chromium extension (Manifest V3) that converts currencies using historical exchange rates from a user-chosen provider (Frankfurter.app or fawazahmed0/currency-api). Vanilla JavaScript, no bundler/build step — `npm` is used only for the Jest test suite, not for running the extension itself.

## Folder layout — the extension and the tooling are deliberately split

```
currency_converter/
├── extension/          # <- load THIS folder as the unpacked extension, never the repo root
│   ├── manifest.json
│   ├── popup.html
│   ├── popup.js
│   ├── providers.js
│   ├── history.js
│   ├── options.html
│   ├── options.js
│   ├── options.css
│   └── styles.css
├── __tests__/          # Jest suite (not shipped)
├── jest.config.js / jest.setup.js
└── package.json / node_modules/   # test tooling only
```

**Chrome's unpacked-extension loader recursively rejects the whole folder if anything inside it — at any depth — has a name starting with `_`** (reserved for the system). `__tests__/` triggers this immediately with "Failed to load extension … Cannot load extension with file or directory name `__tests__`." `node_modules/` would trip the same check via `.bin` and similar entries, and is multiple MB of dead weight in a shipped extension regardless. This is why the extension's files live in their own `extension/` subfolder containing nothing else — keep it that way; don't move test files back to the repo root or add tooling config into `extension/`.

## Commands

```bash
npm install              # install dev deps (also runs "prepare" -> installs husky's git hooks)
npm test                 # run the full test suite once
npm run test:watch       # re-run on file changes
npm run test:coverage    # run with coverage report (target: >80% lines/functions/statements, >75% branches)

npm test -- storage.test.js              # run one test file
npm test -- --testNamePattern="swap"     # run tests matching a name pattern
npm test -- --ci --coverage --watchAll=false   # CI mode

npx sort-package-json    # re-sort package.json by hand (pre-commit does this automatically)
echo "feat: whatever" | npx commitlint   # check a commit message against the conventional-commit rules without committing
```

There is no lint or build command. To run the extension itself (not tested by Jest): open `chrome://extensions/`, enable Developer mode, "Load unpacked", select the **`extension/`** subfolder (not the repo root — see above); after edits, click the reload icon on the extension card and reopen the popup. For popup-scoped debugging, use "Inspect views: popup.html" from `chrome://extensions/`.

**Git hooks (husky v9 + commitlint + sort-package-json)**: `core.hooksPath` is `.husky/_` (set by `npm install`'s `prepare` script running `husky`, which also regenerates that directory — it's self-`.gitignore`d, don't hand-edit it). The two hooks that matter are the plain-text, no-shebang files at `.husky/pre-commit` and `.husky/commit-msg` (husky v9 dropped the old `#!/usr/bin/env sh` + `. "$(dirname -- "$0")/_/husky.sh"` boilerplate — adding it back is deprecated and errors starting in v10): `pre-commit` runs `sort-package-json`, re-`git add`s `package.json` in case it just got rewritten, then `npm test`; `commit-msg` runs `commitlint --edit "$1"` against `commitlint.config.js` (`@commitlint/config-conventional` — standard `type: subject` conventional-commit format, e.g. `fix: correct date range validation`). A commit that fails either check is rejected before it's created.

**Dependencies are pinned to exact versions** (no `^`/`~` ranges) in `package.json`'s `devDependencies`, and `.npmrc` sets `save-exact=true` so a plain `npm install <pkg>` keeps it that way without needing `--save-exact` spelled out each time. When bumping a dependency, edit the exact version directly (or `npm install <pkg>@<version>`, which respects `.npmrc`) rather than reintroducing a range.

## Testing approach

`extension/popup.js` and `extension/options.js` each guard a `module.exports` block at the bottom of the file behind `typeof module !== 'undefined'`, so it's a no-op when loaded as a browser `<script>` but lets Jest `require(...)` them and call their real functions directly — `popup.js` exposes `initializeDOMElements`, `setupEventListeners`, `switchProvider`, `applyConfiguredDefaults`, `resetToDefaults`, `enforceDateConstraints`, `performConversion`, `fetchHistoricalRate`, `displayResult`, `showError`, `renderHistory`, `recordConversion`, `saveFormData`, `loadFormData`; `options.js` exposes `initializeOptionsElements`, `setupOptionsEventListeners`, `applySettings`, `saveSettings`, `loadSettings`. `extension/providers.js` has no `module.exports` — it instead attaches `PROVIDERS`, `DEFAULT_PROVIDER_ID`, `populateCurrencyOptions`, `populateProviderSelect`, `switchProviderCurrencies`, `applyProviderDateRange`, `applyMaxDateToday`, and `todayLocalDateString` onto `globalThis` (a no-op in the browser, where classic `<script>` tags already share one global lexical scope; load-bearing under Jest/Node, where each `require`'d file is otherwise its own isolated module scope). `extension/history.js` follows the same `globalThis` pattern for `DEFAULT_HISTORY_SIZE`, `MAX_HISTORY_SIZE`, `MIN_HISTORY_SIZE`, `addToHistory`, `formatHistoryDate`, `formatHistoryEntry`, and `normalizeHistorySize`. **Any test file that calls a `popup.js`/`options.js` function touching providers must `require('../extension/providers.js')` first** (and `require('../extension/history.js')` too if it can reach `performConversion()`, `loadFormData()` or `saveSettings()`), purely for that global-attaching side effect; it isn't destructured since it exports nothing via `module.exports`. Forgetting this produces a `Cannot read properties of undefined (reading 'value')`-style crash from inside `fetchHistoricalRate` (or similar), not a helpful message.

Because `popup.js` keeps its DOM element references in module-level `let` bindings populated by `initializeDOMElements()`, every test's `beforeEach` must call `initializeDOMElements()` (and `setupEventListeners()` for tests that dispatch real events) after `jest.setup.js`'s global `beforeEach` rebuilds `document.body.innerHTML`, or those bindings point at stale/removed nodes.

Event-driven tests (swap, submit, date-change, provider-change) use `jest.useFakeTimers()` because the real listeners schedule a debounced (500ms) conversion and a 2s "Copied!" revert — without fake timers those become real dangling `setTimeout`s. A shared `flushMicrotasks()` helper (global, from `jest.setup.js`) drains pending promise chains (e.g. the fire-and-forget `performConversion()` a swap/submit/provider-switch triggers) so they can't resolve mid-way through a *later* test and mutate its DOM/mocks; `jest.setup.js` also runs it in a global `afterEach` as a safety net.

`jest.setup.js`'s shared `beforeEach` calls `mockReset()` (not just `mockClear()`/`jest.clearAllMocks()`) on `chrome.storage.local.set/get/remove`, then reinstalls each one's default implementation — this had to be added after a test that called `.mockImplementation(...)` on `chrome.storage.local.get` leaked that custom implementation into a later, unrelated test that assumed the plain default (`callback({})`) and failed confusingly. `jest.clearAllMocks()` alone only resets call history, not a previously-set implementation — `global.fetch` already got the full `mockReset()` treatment for this reason; the storage mocks originally didn't, which is what leaked. If a test sets `.mockImplementation()` on any `chrome.storage.local` method, it's scoped to that one test — the next test starts from the plain default again.

If you extend `extension/popup.js` or `extension/options.js` with a new function you want tested, add it to that file's `module.exports` block — it's easy to forget and end up back in the "tests test a copy" trap this suite was rewritten out of. `extension/providers.js`'s own logic (URL building, response parsing, error messages, currency lists, date-range attributes) has direct unit coverage in `providers.test.js` — extend that file, not `conversion.test.js`, when adding a provider or changing one's request/response handling. `options.test.js` follows the exact same fixture-plus-real-dispatch pattern as the popup suites, against `jest.setup.js`'s `renderOptionsFixture()`.

`storage.test.js`, `conversion.test.js`, and `ui.test.js` all call `initializeDOMElements()` / `setupEventListeners()` / `loadFormData()` directly, so none of them exercise the actual entry point the real extension boots from (`document.addEventListener('DOMContentLoaded', ...)` at the bottom of `extension/popup.js`). `persistence.test.js` covers that gap instead: it `require`s `extension/providers.js` then `extension/popup.js` exactly once (so their `DOMContentLoaded` listeners register in the same order the real `<script>` tags in `popup.html` do) and drives everything by dispatching a real `'DOMContentLoaded'` event via `bootPopup()`, never by calling the internals. It also simulates a popup close/reopen mid-test by calling the shared `global.renderPopupFixture()` (from `jest.setup.js`) to blank the DOM again and re-pointing the `chrome.storage.local.get` mock at whatever the first "session" actually saved — mirroring that storage survives a popup closing even though the DOM and JS module state don't. A bug living only in the bootstrap wiring (wrong listener order, the DOM-not-ready retry path never re-running setup) would pass the other three suites and only get caught here.

Note the limits of even this: a passing Jest suite proves the *logic* works, not that Chrome can load the extension at all, nor that a real network call against the live API actually matches what's mocked. Two real bugs this session were invisible to Jest specifically because of this: the `__tests__`-in-the-loaded-folder failure (Chrome refused to load the extension while every test stayed green), and `host_permissions` missing the fawazahmed0 hosts (Jest mocks `fetch` entirely, so it can't know a real popup's CSP would block an undeclared host — this was only caught by loading the real `popup.html` in `jsdom` with `runScripts`/`resources: 'usable'` and Node's real `fetch` against the live APIs). When "does it actually work" is in question for anything touching Chrome's loader, permissions/CSP, or a live third-party API's actual shape, that's not something the mocked Jest suite can answer — verify it directly (`chrome://extensions/`, or a real-file/real-network jsdom script) before trusting green tests alone.

## Architecture

`popup.html` and `options.html` (both in `extension/`) each load `providers.js`, then `history.js`, then their own page script (`popup.js` / `options.js`) — `providers.js` and `history.js` are the files shared between the two pages.

- **`providers.js`** — defines `PROVIDERS`, keyed by provider id (`frankfurter`, `fawazahmed0`), each entry owning everything specific to that API: its `currencies` list (`{code, name}`), `minDate` (earliest date it has data for), `buildUrl(from, to, date)`, `parseRate(data, from, to)` (throws if the pair isn't in the response), `describeHttpError(status)`, and optionally `buildFallbackUrl(from, to, date)` for a mirror URL. Neither page script assumes a URL format or response shape directly — they only call through this interface, because the two providers agree on almost nothing:
  - **Frankfurter**: `GET /{date}?from=X&to=Y`, uppercase codes, response is `{rates: {Y: rate}}` for just the requested pair. Sources ECB reference rates — **exactly 30 currencies**, historical back to **1999**. No fallback URL.
  - **fawazahmed0/currency-api**: `GET /{date}/v1/currencies/{from}.json` (lowercase codes, `to` unused in the URL), response is the base currency's *entire* rate basket (`{date, usd: {eur: ..., aed: ..., ...}}`) — `popup.js` picks the target rate back out of it. Curated here to **160 currencies** (its full list is 200+, but includes a long tail of crypto tokens deliberately excluded to keep this a fiat-currency picker). **Its per-date snapshots only exist back to 2024-03-02** — going further back always 404s, regardless of currency, which is a real gap relative to the app's "historical" pitch and worth surfacing in error copy rather than hiding. On a failed request it retries against `buildFallbackUrl`'s Cloudflare Pages mirror (the project's README explicitly calls this out as required, not optional).
  - **Adding a provider**: verify each currency code is actually present in that API's own currency-list response before adding it (don't assume ISO 4217 coverage), and add the new host(s) to `host_permissions` in `manifest.json` — a popup/options page's `fetch()` is blocked for undeclared hosts regardless of the target's own CORS headers.
  - `populateCurrencyOptions(providerId)` rebuilds both currency `<select>`s from a provider's list (used by both pages); `populateProviderSelect()` builds the provider `<select>` itself and defaults it to `DEFAULT_PROVIDER_ID` ('frankfurter') — only called on `popup.html`/`options.html` boot, never again, since the *set* of providers doesn't change at runtime (only which one is selected does). `switchProviderCurrencies(providerId, sourceCurrencySelect, targetCurrencySelect)` is the shared "repopulate for a new provider, preserve the current selection where it still exists, else fall back to USD/EUR" logic — it takes explicit element references (rather than assuming fixed globals) specifically so both `popup.js`'s `switchProvider()` and `options.js`'s provider-`change` handler can call the identical logic despite managing different DOM structures.
  - `applyProviderDateRange(providerId)` and `applyMaxDateToday()` (see Date handling below) both no-op if there's no `#conversionDate` on the page, rather than throwing — needed because `providers.js`'s shared `DOMContentLoaded` handler runs on `options.html` too, which has no date field at all.
- **`popup.js`** — the converter's logic, provider-agnostic:
  - `initializeDOMElements()` grabs all element refs (`apiProviderSelect`, `settingsBtn`, `resetBtn`, etc.) into module-level `let` bindings; if the form/inputs aren't in the DOM yet it retries via `setTimeout(..., 100)` rather than failing. `setupEventListeners()` and `loadFormData()` only run after this succeeds, wired from a single `DOMContentLoaded` handler at the bottom of the file. The ⚙ `settingsBtn` just calls `chrome.runtime.openOptionsPage()` — no permission beyond `manifest.json`'s `options_page` key is needed. The ↺ `resetBtn` calls `resetToDefaults()` — see below.
  - `switchProvider(providerId)` sets `apiProviderSelect.value = providerId` explicitly (don't assume it's already current just because the browser sets it before firing `change` — direct calls, e.g. from tests, won't have done that), then calls the shared `switchProviderCurrencies()`. It also calls `applyProviderDateRange()` + `enforceDateConstraints()` (see Date handling below) so an already-selected date that predates the new provider's floor gets clamped immediately. Wired to the provider `<select>`'s `change` listener alongside `saveFormData()` and a conversion trigger, same pattern as swap.
  - `loadFormData()` also self-retries with `setTimeout` if DOM elements aren't ready, and reads **both** `converterData` and `extensionSettings` from `chrome.storage.local` in one `get()` call, checking `chrome.runtime.lastError` on both save (`saveFormData`) and load.
  - **Ordering dependency (provider before currency)**: whenever a provider id and currency codes are applied together — on boot, restoring `extensionSettings`, or restoring `converterData` — the provider must be set (and `populateCurrencyOptions()` run for it) *before* the currency codes are applied, or those codes may not exist yet as `<option>`s under whichever provider is currently populated and silently fail to take. `providers.js`'s own `DOMContentLoaded` handler already populates before setting its USD/EUR defaults; `loadFormData()` does the same for both of its two storage reads (see below).
  - **Configured defaults vs. last-used session**: `loadFormData()` layers two independent storage keys, applied in order — (1) `extensionSettings` (from the Settings/options page, defaults `frankfurter`/`USD`/`EUR` if absent) seeds `apiProviderSelect`/`sourceCurrencySelect`/`targetCurrencySelect` via the shared `applyConfiguredDefaults(settings)` helper, replacing whatever `providers.js`'s boot handler set; (2) `converterData` (the last-used session — provider, amount, both currencies, date), if present, is then applied on top and wins outright. Left at that, a saved session would override Settings forever and changing a setting would look like it did nothing — so `options.js`'s `saveSettings()` also calls `chrome.storage.local.remove('converterData', ...)` right after writing `extensionSettings`, every time any Settings field changes. That means: no session yet → Settings apply; a session exists → it wins, Settings are dormant; the moment Settings are touched → the session is wiped, so the *next* popup open has nothing to restore and falls back to exactly what was just configured. Verify a change here against real, separate `popup.html`/`options.html` jsdom instances sharing one in-memory storage mock, not a single shared Jest `document` — requiring `popup.js` and `options.js` into the same `document` makes both files' `DOMContentLoaded` listeners permanently live on the same elements, so firing that event to simulate "the other page" also re-fires whichever page's listeners were registered first, double-wiring things that are genuinely isolated in real Chrome.
  - **`resetToDefaults()` (the ↺ Reset button)** — the same "revert to configured defaults" idea as above, but user-triggered mid-session instead of only happening at boot. Re-fetches `extensionSettings` fresh from storage (nothing in `popup.js` caches it — it's only ever applied once, at boot, so a stale in-memory copy isn't an option) and passes it through the same `applyConfiguredDefaults(settings)` helper `loadFormData()` uses. Beyond that it also resets `sourceAmountInput` to `'1'` and the date to `todayLocalDateString()` (`applyConfiguredDefaults()` deliberately leaves amount/date alone, since `loadFormData()` needs to leave those to a last-used session when one exists), hides any stale result/error, erases `converterData` the same way `saveSettings()` does — and, unlike `saveSettings()`, then runs a fresh `performConversion()` against the reset values if the form is valid, so Reset shows a live, correct result rather than a blank form. A real (not mocked-`fetch`) end-to-end check of this — configure Settings, use the popup differently, click Reset, reopen — is what caught that an earlier verification script itself forgot to wire `window.fetch` into its `jsdom` instance (silently mis-blamed the 2024-03-02 floor message for a test-harness gap, not a real one); rerun any live check like that with `beforeParse(window) { window.fetch = fetch; }` or a real conversion will always "fail" with that same misleading error.
  - **Same-currency guard**: `performConversion()` rejects `sourceCurrency === targetCurrency` before ever calling the API — Frankfurter/fawazahmed0 both omit the base currency from a same-currency request's response, which otherwise surfaces as a confusing generic "API error" instead of a clear message.
  - **Date handling uses `Temporal.PlainDate`, never `Date`**: `<input type="date">` values are timezone-less `"YYYY-MM-DD"` strings — exactly what `PlainDate` models (a calendar date, no time-of-day, no timezone). This isn't just a style preference: `Date` doesn't have a "just a date" mode, so every previous approach here (`new Date(dateStr)` parses as UTC midnight; `.toISOString()` renders in UTC) mixed UTC and locally-computed values and silently shifted the boundary by the viewer's UTC offset (today rejected as "future", or a reset date landing on the wrong day, for anyone east of UTC) — this actually happened, more than once, before the switch to `PlainDate`. `todayLocalDateString()` (`providers.js`) is `Temporal.Now.plainDateISO().toString()`; date comparisons use `Temporal.PlainDate.from(str)` + `Temporal.PlainDate.compare(a, b)` (see `enforceDateConstraints()`); the human-readable rate line in `displayResult()` uses `Temporal.PlainDate.from(dateStr).toLocaleString(...)`, a drop-in replacement for the old `Date.prototype.toLocaleDateString(...)` call with the identical options shape and output. **Don't reintroduce `new Date(...)`, `.toISOString()`, or `.toLocaleDateString()` for date-input values** — reach for `Temporal.PlainDate`/`Temporal.Now.plainDateISO()` instead; the whole UTC-vs-local bug class is structurally impossible with `PlainDate` since it has no time-of-day or timezone component to hide a mismatch in.
  - **Temporal is vendored, not native yet**: neither Chrome nor Node ships `Temporal` natively at time of writing, so `extension/vendor/temporal-polyfill.js` (from npm `@js-temporal/polyfill`, pinned exact version in `package.json`'s `dependencies` — this is the one npm package that actually ships in the extension, unlike everything else which is dev/test tooling) is loaded as a classic `<script>` in `popup.html`, before `providers.js`. That UMD build exposes `globalThis.temporal.Temporal` (lowercase namespace), not `Temporal` directly — a tiny inline `<script>` right after it promotes `window.Temporal = window.Temporal || window.temporal.Temporal`, a guarded assignment that's a no-op once browsers ship `Temporal` natively (nothing else here needs to change when that day comes — just delete the vendor script tag and the promotion shim). `options.html` doesn't load it: nothing on that page calls a `Temporal`-touching function (`applyProviderDateRange()`/`applyMaxDateToday()` both no-op before reaching `Temporal` when there's no `#conversionDate`, which `options.html` doesn't have). Jest/Node gets the same package a different way — `jest.setup.js` does a plain `require('@js-temporal/polyfill').Temporal` and assigns it to `globalThis.Temporal`; this only works because `@js-temporal/polyfill` ships a real CJS build. The newer, lighter `temporal-polyfill` package was tried first and reverted — it's ESM-only (`"type": "module"`, no CJS export), and Jest's module system refuses a dynamic `import()` of an ESM package without `--experimental-vm-modules`, which wasn't worth forcing on this project for one dependency.
  - **Date range enforcement**: the date `<input>` is bounded on both ends, each with a native-attribute primary defense plus a JS-level secondary one (same two-layer pattern for both):
    - **Floor, per-provider**: each provider entry in `providers.js` has a `minDate` (Frankfurter: `'1999-01-01'`; fawazahmed0: `'2024-03-02'`, its actual earliest daily snapshot — not 1999, despite the app's general historical-data framing). `providers.js`'s `applyProviderDateRange(providerId)` sets the input's native `min` attribute so the picker itself won't offer an earlier date.
    - **Ceiling, fixed at today**: `providers.js`'s `applyMaxDateToday()` sets the input's native `max` to `todayLocalDateString()` (the same local-calendar-day helper used for the default date value) — runs once at boot; a popup session is too short-lived for "today" to roll over mid-session, so nothing re-applies it later.
    - Neither native attribute retroactively fixes a value set before it was applied (typed, restored from storage, or already selected before a provider switch tightens the floor) — that's what `popup.js`'s `enforceDateConstraints()` is for: rejects a future date (clamped to today) and a too-early one (clamped to `provider.minDate`), each with an error message. Called from the date `<input>`'s `change` listener, from `switchProvider()`, and defensively at the end of `loadFormData()` (in case a provider/date pair was saved out of sync, e.g. by a version of the extension that predates one of these fields).
  - Conversion flow: form submit, debounced (500ms) input change, or a provider switch → `performConversion()` validates inputs → `fetchHistoricalRate(from, to, date)` looks up the currently-selected provider and calls its `buildUrl`/`buildFallbackUrl`/`parseRate` → `displayResult()` multiplies amount × rate and renders. No backend, no API key for either provider.
  - State persistence: a single `chrome.storage.local` key, `converterData` (`apiProvider`, amount, source/target currency, date), saved on every relevant input/change event.
  - **Recent conversions**: a separate `chrome.storage.local` key, `conversionHistory` — an array of `{apiProvider, date, rate, sourceAmount, sourceCurrency, targetCurrency}`, newest first. `performConversion()` calls `recordConversion()` after each *successful* `displayResult()`, which re-reads `conversionHistory` + `extensionSettings` fresh, prepends via `history.js`'s `addToHistory()` (skips a repeat of the top entry; trims to `extensionSettings.historySize`, default 10, clamped 1–100 by `normalizeHistorySize()`), saves, and re-renders. `loadFormData()` also renders it on boot. Rows are built with `textContent` (stored data, never `innerHTML`) in the `dd/MMM/yyyy` format `formatHistoryDate()` builds by hand — not `toLocaleString()`, which can't produce that exact pattern. `styles.css` gives rows a fixed height so `.history-list` caps at exactly 10 visible rows and scrolls beyond. Neither Reset nor `saveSettings()` clears `conversionHistory`.
- **`options.js`** — the Settings page, structured like a smaller `popup.js` (`initializeOptionsElements()` / `setupOptionsEventListeners()` / a `DOMContentLoaded` boot handler / a `module.exports` guard), but with its own DOM (no form, no amount/date, no swap/copy) and its own storage key. `extensionSettings` holds `apiProvider`, `historySize`, `sourceCurrency`, `targetCurrency`; a `historySize` change saves with `saveSettings({ clearSession: false })`, since it isn't a popup default and has no reason to wipe `converterData` — the other listeners call `saveSettings()` through an arrow wrapper so the `Event` isn't mistaken for that options argument. Saves on every `change` (no explicit Save button, same immediate-persistence pattern as the popup), showing a brief "✓ Saved" message via `#savedMessage` (`saveSettings()`'s `setTimeout` revert, same idea as the popup's "Copied!" button) — but only after `chrome.storage.local.remove('converterData', ...)` has also completed; see popup.js's "Configured defaults vs. last-used session" above for why that removal exists. Its provider-`change` handler calls the shared `switchProviderCurrencies()` from `providers.js` — same reconciliation logic as `popup.js`'s `switchProvider()`, just without the date-range/conversion side effects the popup also needs.
- **`options.html`** — reuses `styles.css` for shared look, with `options.css` overriding the popup's fixed 420px width for a centered full-tab layout (this page opens in its own browser tab, not a small popup, via `manifest.json`'s `options_page` key).
- **`popup.html`** / **`styles.css`** — markup and presentation only, no embedded logic.
  - **Explicit tab order**: the form's grid layout (below) doesn't follow the DOM order, and DOM order alone no longer reflects the intended tab sequence either — `apiProvider`, `sourceCurrency`, `sourceAmount`, `targetCurrency`, and `swapBtn`/the submit button carry explicit `tabindex="1"`–`"6"` (in that order) rather than relying on source order. `conversionDate`, `resetBtn`, `settingsBtn`, and `copyBtn` are deliberately left with no `tabindex` (default `0`) — they're reached by DOM-order tabbing only after all six positive-`tabindex` elements, per normal HTML tabbing rules. If you add or reorder a form field, don't assume moving it in the HTML changes its tab position — update its `tabindex` (and the others', if you're inserting into the middle of the 1–6 sequence) explicitly.
  - **Grid layout**: `form` is `display: grid` with named `grid-template-areas` — one area per class added to each `.form-group` (`apiProvider`, `sourceAmount`, `sourceCurrency`, `targetCurrency`, `conversionDate`), matching each field's own `id`; `.btn-swap`/`.btn-convert` reuse their own existing classes as their area names instead of getting a new one. Current layout: provider (full width) → source currency + source amount → target currency + swap button → date (full width) → submit (full width). `grid-template-columns` is explicitly `minmax(0, 1fr) ...` (2 columns), never a bare `1fr` or omitted (which defaults to `auto`) — either lets a track grow to a child's intrinsic max-content width, and the provider `<select>`'s longest option text is wider than the whole popup, which blew out the entire grid (and the popup itself) the first time this shipped without it. `.form-group` also needs `min-width: 0` for the same reason — grid items default to `min-width: auto`, which alone would still defer to that same intrinsic width and silently undo the track fix.
